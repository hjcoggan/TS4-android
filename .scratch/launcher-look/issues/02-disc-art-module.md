# 02: Disc art module

**What to build:** The Disc art module in Launcher.Core. Given a disc `.iso` or the prepared disc folder, it decodes the images ticket 01 recommends and writes them as PNG to an `art` folder in the per-user folder, with a multi-size `.ico` from the title icon and a small index naming what was found and the disc it came from. When the setup page accepts a disc, the art is read from the `.iso`; a failure is logged and never fails the disc row. Spec: `.scratch/launcher-look/spec.md` (Implementation Decisions "Disc art module", "Setup hook"); format details in `docs/research/disc-art.md`.

**Blocked by:** 01 (Disc art inventory); `.scratch/launcher-ux/issues/04-setup-page-check-on-pick.md` (the disc row's accept step)

**Status:** resolved

- [x] Launcher.Tests: fixture packages generated in the tests (no game art) give the PNGs, the `.ico` and the index; a package without the image gives no file and no error; a damaged package gives a logged reason and no file
- [x] Launcher.Tests: accepting a disc on the setup page writes the art; an art failure leaves the disc row accepted
- [x] Run once against the owner's `.iso`: the art folder holds the four images, each matching ticket 01's evidence (five, after the spec amendment)
- [x] `pwsh scripts/build.ps1 -Action Check` passes

### Review fixes

2026-10-28, after the code review of `815cfac...launcher-look`. Each bug has a test that failed against `951de19` first (the new tests run in a scratch copy of that commit), then passes:

- Any failure decoding a source is a logged problem (was: only IO, access and invalid-data errors were caught, so a decoder's other exceptions could escape `FromFolder`, `FromIso` and `RestoreFromFolder`). `DiscArtDamageTests`: a source that throws a crypto, null-reference, argument, overflow, invalid-operation or not-supported error is logged as `Disc art: <source> ...` and the other sources still count. No single-byte corruption of a generated Module's header reproduced an escaping exception on the old code (87 s of fuzzing), so this one is closed by the contract, not by a found input. The test uses the internal `IDiscFileSource` seam (`InternalsVisibleTo Launcher.Tests`, new `DiscArt.FromSource`). A write failure (IO or access) is now a logged problem too, not an exception.
- Writes to the art folder are serialised (`DiscArtFolder.WriterLock`; `RestoreFromFolder` checks and reads under it) and every temp file has a unique name (`<file>.<guid>.tmp`), removed on failure; stray `*.tmp` files a crash left are removed at the next write. `DiscArtFolderTests`: 40 overlapping `FromFolder` calls from two discs, and `FromFolder` with `RestoreFromFolder` overlapping, give no problem and no `.tmp` (the old code failed with a sharing violation on `background.jpg.tmp`).
- `DiscArtFolder.Write` order is now: the new image files, then `index.txt`, then the files the new disc has no use for. A write that fails half way (a window holding `logo.png` open) leaves the earlier index, its files and its stamp as they were.
- `IsComplete` is now "an index from a read with no logged problem exists, and every file it lists exists" (`index.txt` gained `read=complete`). A disc that genuinely lacks an image, or has no art at all, is read once and then left alone; a deleted listed file, a missing index, or a read that logged a problem is read again.
- `DiscArtFolder.Stamp` (index lines plus each listed file's size and write time) says when the folder changed, also under the same file names; `Has`, `Found` and `Source` are gone (tests use `ImagePath` and read `index.txt`). `default.xex`'s header is parsed once (`XexTitleImage.Read(xex, execution)`), and `MaxFileBytes` is one constant (`IDiscFileSource.MaxFileBytes`).
- Run against the real prepared disc folder (`%LOCALAPPDATA%/TopSpin4Recomp/gamedata`, read only) with `DiscArt.RestoreFromFolder` into a scratch art folder: 81 ms, no log line, `IsComplete` true, all five images SHA-256-equal to `analysis/disc-art/` (`nxeart/nxebg.jpg` `DDA13DF7...`, `nxeart/nxeslot.jpg` `611C4BB4...`, `xzp-PressStart/Bitmaps/Logo.PNG` `49CA0753...`, `Bitmaps/PressStart.PNG` `9B40DE41...`, `xex-spa/img_8000.png` `1EBD006C...`); `topspin4.ico` 8,233 bytes; a second restore did nothing. The real per-user folder was not touched.
