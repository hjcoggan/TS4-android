# 07: Hand-off to Swing

**What to build:** Swing is built as its own host library. Loader loads it, then unloads itself while exiting its thread, and Swing's main loop starts.

**Blocked by:** 06 (Loader loads and runs)

**Status:** ready-for-agent

- [x] Swing is a module entry compiled to a separate host library
- [x] Loader's load of Swing and the unload-and-exit-thread hand-off work
- [ ] Swing's own module load and unload calls are handled, and loading any module outside the Reference build is refused cleanly
- [x] The smoke run shows Swing's main loop running with no unregistered call targets on the boot path
- [x] Any ReXGlue fixes needed are numbered patches

## Comments

- 2026-10-24 (Claude): Swing is a `[[modules]]` entry built as `topspin4_Swing_DLL.dll` (47,081 functions; 5 seeds from analysis errors, 60 reviewed from the seed finder; CRT `setjmp`/`longjmp` at `0x8856B7F0`/`0x88569D30`). The hand-off in TU1 is simpler than the import list suggested: Loader calls Swing's entry on its own thread, and its only `XexUnloadImageAndExitThread` call sits in a wrapper (`sub_8340AF50`) that nothing calls or references, so Loader stays resident. The runtime's stub for it is never reached. Swing's `XexLoadImage` calls go through the runtime's module path; `patches/rexglue/0027-refuse-unrecompiled-modules.patch` makes any module without a recompiled library (a DLC replacement DLL, say) fail to load as if absent, with an error line, instead of faulting on its first call. Not exercised on the boot path yet. Smoke: Swing loads its archives, starts its worker threads and presents 1280×720 frames at 60 fps with no unregistered call targets, but the screen stays black after `XNetLogonGetTitleID` (stub), which is where ticket 08's title-server hooks come in. Rebuild isolation: touching Swing's generated code rebuilds only Swing.
- 2026-10-24 (Claude), after review: two boxes unticked. Loader's load of Swing works, but the unload-and-exit-thread hand-off was never exercised: TU1 never calls it on the boot path, and the runtime's `XexUnloadImageAndExitThread` is still a stub. It needs a real implementation if any path reaches it. Swing's own `XexLoadImage`/`XexUnloadImage` calls have not been seen in a run yet. Patch 0027 matched modules by file name only, so a same-named module from another device (a DLC package's `Swing_DLL.xex`) would have been wired to TU1 code. `0028-modules-from-own-folder` now refuses any module outside the executable's own folder, comparing the folders as the VFS resolves them. Boot, Loader and Swing still load. The refusal itself has not been exercised. Rebuild isolation was also checked through the manifest: a seed change reruns codegen for all Modules, but unchanged Modules' sources are not rewritten, so nothing of theirs rebuilds.
- 2026-10-25 (Claude), ticket audit: breakpoints on the runtime's `XexLoadImage` and `XexUnloadImage` during a headless run to the main menu show TU1's real hand-off. Swing (`sub_887CBB18`) calls Boot's export `sub_82029038`, which takes the handle Boot stored when it loaded `game:\Loader_DLL.xex` (`sub_82029358`), calls Loader's export #3, then unloads Loader with `XexUnloadImage` (`sub_82012398`) and clears the handle. The game carried on to the main menu and exited cleanly at frame 1400. `XexUnloadImageAndExitThread` is not on this path: it is a `REX_EXPORT_STUB`, and no stub warning appears in any run. So the hand-off box is ticked as TU1 does it. Swing's own module calls: it loads `xam.xex` (a system module, through its `LoadLibrary`-style wrapper `sub_8857A070`) and unloads Loader through Boot, both handled. The last box stays open only for its refusal half: no run has tried to load a module from outside the Reference build, so patches 0027 and 0028's refusal is still unobserved.
